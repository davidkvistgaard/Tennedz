# First real two-phase simulator output committed in isolation

The allowlisted isolated Supabase project `nxhvaoonnvmvohqaxfdx` completed a disposable two-team, 16-rider two-phase race with the **actual JavaScript simulator output**. `tests/support/two-phase-real-output-setup.sql` created the event, teams and riders, closed registration, persisted the point-based division reveal, locked tactics and returned the private immutable race snapshot. `tests/support/simulate-two-phase-snapshot.mjs` built one recorded division locally. The service-only `recovery_finish_race` RPC then atomically saved that output from the locked input.

The saved event was `FINISHED` with two team results, 16 rider results, one recorded replay, 16 earned-point awards and one race commit. Team rating totals equalled their saved result points (185); rider rating totals equalled their saved points (818). A repeated finish call returned `already_finished: true`. `tests/support/two-phase-real-output-cleanup.sql` removed the exact named event and its children, then all 16 disposable riders and two teams. Follow-up counts for the event, its commits, reveal, lock, awards, named teams and riders were all zero. Both private local JSON files were deleted.

The setup and cleanup files are a paired isolated-project probe, **not** migrations. Unlike the rollback-only probes, setup persists a fixture across the simulator round trip; always run cleanup with the returned event ID, even if simulation or finish fails. The cleanup refuses an event with a different name or roster size. Never print, commit or upload the returned private snapshot or output. This verifies one complete database-to-simulator-to-database two-phase chain. It does not yet cover 45 independently authenticated managers in this flow, three actual simulator outputs committed together, tactical balance, or production readiness. Production Supabase, Vercel and live data were untouched.
