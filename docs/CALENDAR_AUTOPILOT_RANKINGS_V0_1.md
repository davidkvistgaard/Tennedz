# Calendar, autopilot and rankings V0.1 — implementation boundary

This package extends the existing `events`, `event_teams`, rider and team records. The new race engine remains isolated. Nothing here deploys a race schedule or changes live data.

## Implemented in this branch

- The Wednesday/Sunday placement utility maps source one-day dates into the same calendar week, retaining source dates as metadata. Stage races remain exempt from the two weekly one-day slots. A shared pair ID can relate distinct men's and women's events without combining their fields.
- The existing administrator race-day creator now has an additive scheduled path. It writes source, tier, scheduled day, team size and the optional UCI source metadata atomically with the established route/event creation. Legacy requests retain their existing behavior; the editor creates original Pelotonia races and requires Wednesday or Sunday.
- The race calendar shows separate event cards, filters, entry and order readiness, tier points and a direct link into the existing one-day team/order page. An event with no scheduled date is explicitly shown by its existing entry deadline.
- The calendar passes its active filter into the one-day order page, and the return link restores that filter.
- Stage-race cards show the configured final GC, stage, points-classification and mountain-classification curves without implying that stage setup or result awards are already operational.
- The team home card now chooses the next scheduled one-day race for the selected squad, shows actual team/order readiness and points tier, and opens that exact event. Legacy events without a race date remain a fallback and are labelled by entry deadline.
- Managers can save four gender/format default squads with a captain. The server validates ownership, full team size, distinct riders and current roster membership. A deterministic resolver replaces unavailable defaults from eligible teammates and refuses to invent riders.
- A guarded one-day autopilot executor can preview or submit one team/event through the existing transactional join and order validator. An administrator-only batch endpoint walks at most 25 teams at a time with a cursor and reports individual skips without losing progress. It only acts on a saved default, keeps explicit entries authoritative, and holds same-gender same-day conflicts for a future priority rule. The database repeats those last two checks under the join lock, preventing a concurrent manual entry from being overwritten. Both write endpoints also require the existing game-write flag.
- A daily Vercel cron endpoint now claims eligible races within 48 hours of their entry deadline, processes short batches, and advances a persistent per-race cursor. A database lease prevents concurrent workers from claiming the same page; failed pages retry after lease expiry. Completed races are scanned again on a later run so a manager who saves defaults afterward can still enter before the deadline. It requires `CRON_SECRET`, `PELOTONIA_AUTOPILOT_ENABLED=true`, and the existing game-write flag. The new flag defaults to off. No cron has been deployed or enabled in production.
- With both flags enabled, a one-day default save also attempts entry into matching open races whose deadlines fall within 48 hours. This addresses a save after the day's cron run. The response distinguishes the saved default from confirmed entries and warns if the immediate attempt fails or exceeds its eight-race cap.
- When autopilot is enabled, the administrator's scheduled-race creator now uses a service-only guarded RPC. New races need a deadline after the next 02:00–02:59 UTC cron window plus ten minutes; an existing request ID remains idempotent. The regular creator stays available while autopilot is disabled. This removes the known late-creation timing gap but does not guarantee the cron will succeed or finish all teams.
- One signed points ledger carries the rider, credited team, event, season, gender, source, format, tier, result type, place and policy version. Filtered rider and team rankings aggregate that ledger, including combined team points. Reversal rows preserve the audit trail.
- Race tier and placing values live in `lib/calendar/points.mjs`, separate from the engine. Inactivity thresholds and default team sizes live in `lib/calendar/config.mjs`.
- The additive migration creates the required private tables and read RPCs; no existing events or results are rewritten.

## Still required before the package is operational

### Division matchmaking for a calendar race

One calendar race needs two separate deadlines before the start:

1. **Registration:** Teams enter before the registration deadline. A valid provisional eight-rider lineup and captain can support the existing entry and fee rules; managers may revise the lineup and orders later. Manual and autopilot entries share this pool. The autopilot queue must target the registration deadline, and a backlog must be resolved before division assignment rather than silently omitting eligible teams.
2. **Division reveal and preparation:** After registration closes, freeze entrants and their season/gender team-point snapshot, then assign divisions. Show each manager their opponents, point levels and the route. Keep opponents' private orders hidden. Allow lineup, captain and tactical changes until a later tactics deadline; charge the entry fee only once. Division membership must not move when a manager changes tactics or when rankings update in the meantime.
3. **Tactics lock and race:** At the tactics deadline, validate and freeze each entered team's final riders, captain and orders. A still-valid provisional lineup/default orders provides a defined fallback when a manager does nothing. Only then run and record each division. Registration, tactics and race dates need an explicit minimum preparation interval; its length requires playtesting rather than an assumed fixed value.

At division reveal, the server assigns entrants to separate, independently simulated divisions of at most 20 teams on the same course. Men's and women's events keep separate entrant pools and ranking points. Thus 45 entrants in one event produce three race instances, each with its own viewer, classification and result, while the calendar still presents one parent race. Division assignment must use a frozen snapshot of **earned team ranking points for that gender and season** at registration lock, with a stable tie-breaker. The current one-day runner already makes balanced groups of at most 20 (15/15/15 for 45 teams), but seeds by roster ability (`teamRating`); it does not yet implement points-based matchmaking or the separate preparation phase. The isolated test project now awards earned points for finalized one-day races; the additive migration is not in production. The current join/order flow uses one deadline for entry, lineup and tactics, so it must be split at both API and database validation layers.

`lib/calendar/division-reveal.mjs` now provides the isolated assignment calculation for a caller-supplied event/season/gender points snapshot. It validates distinct entrants and non-negative integer points, ranks by points with a stable team-ID tie-breaker, and balances 45 teams into 15/15/15. It does not fetch or persist the snapshot, set phase deadlines, or change the existing one-deadline runner. Zero-point entrants currently tie by ID in this calculation; that is a deterministic fallback for tests, **not** the approved provisional-placement policy for live matchmaking.

`lib/calendar/race-phases.mjs` defines the future two-deadline phase boundaries from explicit, time-zone-aware timestamps. Registration ends exactly at its deadline; preparation runs until the tactics deadline; tactics are then locked until the scheduled start. It enforces the ordering but no minimum preparation duration, which still needs playtesting. No database column, endpoint or UI consumes these phase rules yet.

The one-day simulator can now take an explicit `points_at_registration_lock` snapshot for isolated tests. It rejects a snapshot from another event, category or scheduled UTC season, or with a missing or foreign entrant; it records the resulting `division_reveal` and simulates those point-seeded groups even if roster strength subsequently changes. Callers that omit it retain the existing ability-seeded behavior. The live race path does not yet supply or persist this snapshot, so no production matchmaking behavior changes.
The simulator can also consume a saved `locked_division_reveal` containing the frozen point values and assignments. It validates those assignments against the frozen values and exact entrant set before using the saved group membership; altered or missing assignments fail closed. The live snapshot RPC does not yet supply this field.
The separate phase helper requires a persisted division reveal before reporting preparation and a persisted final tactics snapshot before reporting tactics locked or race due. A registration deadline alone leaves the event in `reveal_pending`; a tactics deadline alone leaves it in `tactics_lock_pending`, even after the scheduled start. The helper is not connected to the live calendar yet; the eventual caller must derive both commit flags from stored transactions rather than request input.

Balanced adjacent groups (for example 15/15/15 for 45 entrants) keep the lowest division meaningful rather than creating a five-team leftover. Confirm the final sizing and point-reward policy during multi-team playtests. New teams and teams tied at zero points need a provisional placement rule; the rule must not let a strong team deliberately shed points to farm an easy division. A late entry or ranking update must never reshuffle divisions after lock. The 45-team end-to-end test must verify registration lock, reveal, post-reveal order changes, tactics lock, assignments, isolated results/replays, points and repeat-run idempotence.

The next implementation should keep the transaction boundaries explicit:

1. Add separate registration and tactics timestamps only for races opting into the new flow. Legacy events with no new timestamps retain the current deadline behavior. Store a private, event-scoped reveal record with its season, gender, point-policy version, frozen entrant/point snapshot and division assignments; restrict direct client access.
2. At registration lock, serialize with manual joins, autopilot joins and race commits. Resolve or report an unfinished autopilot queue before reveal. Capture entrant IDs and earned team points for the event's season and gender once, then persist balanced assignments from that captured snapshot. A retry must return the saved reveal, not recalculate from newer rankings. Resolve the zero-point/provisional placement rule before enabling this path.
3. After reveal, reject new entries in the database while allowing an entered manager to change lineup, captain and orders until the tactics deadline. Keep existing fee receipts idempotent. Opponent names, point levels and route may be public to participants; opponent orders remain private.
4. At tactics lock, validate every final entry and persist a frozen race input or documented fallback. The runner must use the saved division membership and reject a missing or mismatched reveal; the atomic finish still compares its complete input snapshot and prevents duplicate results or awards.
5. Exercise late join and late order attempts, unfinished autopilot work, concurrent reveal and start calls, a ranking change after reveal, 45 entrants across three divisions, own-viewer isolation, award totals, rollback on failure and repeat-run idempotence in the allowlisted test database before any production proposal.

- Verify and apply the migrations on an isolated Supabase test database, then populate a reviewed UCI/Pelotonia schedule with real source dates and profiles. The editor can create individual original Pelotonia events; no UCI import or season-generation job exists yet. Legacy events remain unclassified until individually reconciled.
- Verify the scheduler against an isolated database and measure whether a once-daily 60-second run covers the actual team/event volume before enabling it. The persistent queue retries transient failures, but capacity and deadline coverage at global scale remain unproven. Saving defaults alone does **not** submit entries while the flag is off. Resolve simultaneous-event priority and rider availability across overlapping stage races before enabling unattended participation at scale.
- The isolated one-day commit now writes idempotent tier/placing awards with the recorded division multiplier, and filtered rankings sum the credited riders for each team. The additive migration is not in production. Stage-race GC, stage and classification awards are still unconnected. Existing rider ability ratings remain separate and are not converted into sporting points.
- Integrate stage-race setup, per-stage status and the GC/stage/classification point preview into the calendar. The current direct setup covers one-day events.
- Make four default squads part of onboarding only after the automatic-entry path and migration are verified. Introduce inactivity transitions, archival and rider release only with the transfer system; do not delete historic competitors.
- Feed real ranking positions and ongoing stage-race state into the team home screen after awards and stage lifecycle are available. Movement indicators require prior snapshots and are not fabricated.

No live Supabase or Vercel operations are part of this branch. Existing P02 and one-day points migrations were checked in the isolated database; the proposed two-phase schema and transaction changes above have not been implemented or applied anywhere.
