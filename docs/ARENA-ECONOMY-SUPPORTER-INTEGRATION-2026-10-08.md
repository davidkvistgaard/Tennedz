# Arena Sealed, Gold, Gems and Supporter — integration plan

**Status: design integration only, 8 October 2026.** Source of product decisions: [the consolidated handoff](PELOTONIA_ARENA_ECONOMY_SUPPORTER_CODEX_BRIEF_V1.md). This plan does not authorize a paid feature or a production rollout. The handoff distinguishes agreed rules from provisional examples and open decisions; it remains the source for those distinctions.

## Existing implementation and gap

- The current authenticated manager owns a persistent team. Calendar events, entries, point-based division reveals, preparation deadlines, locked tactics, recorded v2 candidates and an isolated settlement path already exist. Production still uses the older race path. V91 and the short-step finale remain candidates with unfinished sporting acceptance and end-to-end result/point consistency. Arena must not advance the normal motor release gate.
- `simulateTacticalTour` already accepts two to twenty teams of eight riders, a seeded route/weather snapshot and normalized orders. `normalizeOrders` already validates the eight-rider lineup, captain, presets and phase orders. The route contract accepts 20–400 km with profile, surface, exposed sections and locked weather. Arena should adapt temporary inputs to these contracts and reuse the same versioned recording validator.
- Normal calendar registration, division reveal, career riders and the sporting point ledger assume scheduled events and persistent teams. Arena is on demand, uses temporary sealed riders and awards no career Gold or ranking points. Give it separate lobby, temporary-pool, entrant, lock, recording and result records, with explicit links to the reused route/order/engine versions. Do not insert Arena awards into the career point ledger.
- The existing private v2 viewer authorizes entered managers and exposes only their division. Arena needs its own post-lock participant/spectator access policy and a replay projection that never reveals secret pre-race orders. Its viewer must play the immutable computed recording; it must not simulate again.
- Basic club palettes/patterns are already free, persisted club identity. The Supporter kit studio is only a browser-local design preview. Preserve the existing free choices when defining cosmetic entitlements. No Gold/Gems wallet, Supporter entitlement or payment flow is established by the present backlog or API inventory; the current sporting point ledger is not an economy ledger.

## Agreed product boundaries to preserve

1. Arena Sealed v1 gives each manager an individual, approximately balanced temporary pool of **8, 12 or 16** riders. Each starts exactly eight. Eight-pool means all eight start; twelve/sixteen allow selection. Shared Draft is later scope. Pool balance method and exact skill-cap semantics are open.
2. Arena races use one gender only. Host settings include terrain, distance, rider skill cap, pool size and manager capacity, validated against actual route/engine capabilities. Example values and the suggested twelve-rider default are provisional.
3. Launch reveals the route and each manager's own pool. Preparation shows all opponent pool riders by name and engine-derived archetype, but no exact stats, chosen eight, roles or orders. After lock, show actual start lists and archetypes; orders remain secret. The engine computes once at start/lock, with documented safe fallback for an unready manager, and the viewer replays that saved computation.
4. Gold is earned/spent in the persistent sporting economy and cannot be bought with cash or Gems. Gems are a separate potential premium resource; there is no Gold↔Gems exchange. Arena outcomes grant neither Gold nor career ranking points. Keep economy, entitlement and reward records separate and auditable.
5. Supporter is **one account-level entitlement**, independent of Gems, with monthly, six-month and twelve-month terms offering the same features. Expiry preserves created designs and history. It cannot buy stronger riders, faster progression, exclusive competitive tactics or materially superior competitive intelligence. The quoted DKK prices are provisional examples, not implementation values.
6. Actual Gems purchase, paid entry, entry-funded or outcome-dependent prizes, transfers/redemption and a platform share remain legally and commercially unresolved. Prototype only with free entry or non-purchasable, non-redeemable test credits; do not deploy real-money related features without explicit approval after jurisdiction-specific legal/payment review.

## Incremental order

**A. Protect the current race chain.** Finish point 04/11 sporting acceptance and the versioned short-step result/recording/point contract. Keep the current production game and older recordings intact. At the same time, define an Arena adapter contract: temporary rider IDs and attributes, route snapshot, order version, deterministic seed, privacy fields and a competition-type discriminator. This is design and test work, not a second engine.

**B. Free Sealed domain prototype.** Build host/create/join and browse/share of free lobbies, bounded configuration, atomic capacity/duplicate-entry checks and cancellation states. Generate each sealed pool once from stored seed and versioned rules; test distributions and approximate fairness across terrain and caps. Keep temporary riders out of career roster, transfers, training and Gold. Reuse the existing eight-rider order validator and UI after adapting its data source. Define and test a safe unready-manager fallback before allowing automatic lock.

**C. Lock, run and view.** Freeze route/weather, pools, selections and orders under one deadline/ready transition. Run the same versioned engine once and save immutable per-lobby recording, results and a non-career audit record. A retry returns the same result. Expose separate participant and spectator projections with preparation secrecy and post-lock start-list rules. Add a spectator-capable viewer only after the recording contract is trustworthy.

**D. Harden the free mode.** Test concurrent joins/locks, ownership, data isolation, duplicate requests, deterministic replay, capacity, pool fairness, failed launch and cancellation, route/skill-cap validation, performance for supported field sizes, accessibility and abuse/observability. Preview flags and isolated test data first; production only after a separate release review.

**E. Persistent economy and Supporter.** Point 28 designs Gold sources/sinks, budget guards and anti-abuse without inventing rates. Point 31 adds a manager-level Supporter entitlement and expiry-safe cosmetic/convenience features after payment and security review. Do not gate basic competitive tactics or remove the currently free saved club kit. Supporter access to Arena remains undecided.

**F. Gated monetization and later Draft.** No paid Gems entry or prize pool is part of the free prototype. Only after explicit product decisions, legal clearance and approval should purchasing, entry accounting, prize distribution, refunds, anti-collusion and platform share be designed and implemented. Shared Draft and richer tournaments remain later scope.

## Decisions still required

Arena eligibility versus Supporter gating; exact Supporter feature list and final prices; Gold sources, sinks and rates; sealed-pool balancing and stat-cap semantics; lobby size/distance presets; launch, ready, deadline, fallback and cancellation/refund rules; whether exact opponent stats ever become public; spectator privacy/result-reveal behavior. Gems purchase packages, stakes, reward curve, rake, transferability/redemption and any actual paid-prize operation require product decisions **and** legal/payment review. None of these values should be silently set by code.
