# Isolated point-based division reveal

`20261005063214_persist_point_division_reveal.sql` adds a service-only `recovery_commit_division_reveal(event)` transaction for opted-in two-phase one-day races. It uses the same advisory transaction lock as entry and race commits. It refuses legacy events, races outside the reveal window, existing results, and an incomplete autopilot entry scan. The scan must already have a `COMPLETE` job row; the current daily cron does not yet guarantee a final scan at registration close, so no live caller is enabled.

The transaction freezes the exact entered team IDs and their signed **team** ranking points for the event's UTC season and gender, considering awards timestamped no later than registration close. It writes one parent reveal and one row per team with points, division index and seed rank. Seeds sort by earned points descending, then team UUID ascending. The zero-point tie rule is explicitly versioned `provisional-zero-point-id-tiebreak-v1`; it is a deterministic test fallback, **not an approved live placement policy**. Division sizes use the same balanced maximum-20 rule as `assignPointDivisions` (45 teams become 15/15/15). A retry returns the stored rows without inspecting current standings. Service-role delete rights on reveal records are removed.

The migration was applied only to isolated Supabase project `nxhvaoonnvmvohqaxfdx`. `tests/support/division-reveal-probe.sql` passed against that project. It uses a rollback-only two-team fixture to check missing-scan rejection, pre-deadline award inclusion, post-deadline award exclusion, and identical retry; it checks the integer sizing formula for every pool size from 2 through 400, including 45 → 15/15/15. Afterwards the project still had zero opted-in events and zero saved reveals. Security and performance advisors found no new exposed reveal access or missing reveal foreign-key index. The RLS/no-policy notices for deliberately private tables remain expected.

This does not enable the two-phase UI or race engine. Before a playable test: finish the registration-close autopilot sweep, resolve the zero-point placement policy, permit private lineup/order edits only during preparation, freeze the final tactics input in another persisted transaction, and supply both saved snapshots to the simulator. The existing opt-in result guard stays active; production Supabase is untouched.
