# P03 — first isolated 45-team race chain

This is a repeatable test of the **existing one-deadline one-day flow**, not the planned two-phase registration and tactics system. It uses only the allowlisted Supabase project `nxhvaoonnvmvohqaxfdx`, a local production build and disposable accounts. No production database, deployment or live race was changed.

## Verified

- `tests/support/p02-isolated-teams.mjs seed 45` created 45 separately owned teams. `tests/support/p03-multidivision.mjs seed` attached eight distinct male riders to each team and submitted 45 entries through `recovery_join_event_with_orders` with a captain and valid default orders. The isolated database recorded 45 entry-fee receipts, one per team.
- A local production server with game writes enabled **only for the test project** ran the race through `/api/admin/run-event` after the entry deadline. The API returned three divisions of 15 teams. `/api/event/results` returned 15 team and 120 rider results per division. `/api/event-run` returned three persisted replays, each containing exactly the riders and teams in its own result. A second admin call reported `already_finished:true`.
- The database independently confirmed 45 entries, 45 receipts, three division runs, 45 team results, 360 rider results and one race commit. The fixture event and its results, receipts and replay, all 360 added riders, and all 45 added accounts and teams were removed. Counts returned to 11 events, seven teams, 13 historical entries, five historical division runs/commits and zero P03 riders or temporary accounts. Local fixture ledgers were removed.
- The unit simulation additionally checks deterministic output, balanced 15/15/15 grouping for 45 entrants, no duplicated riders or teams, and replay rosters matching the separate division results.
- `tests/support/p03-browser.mjs` logged into the local production build as one of the 45 temporary managers, loaded its real saved lineup, changed the team plan to breakaway and one rider's effort to aggressive, saved through the player UI, reloaded and confirmed the order in both UI and database. The same browser then followed that manager through the finalized 45-team race, its own recorded division viewer and results/points screen. There were no uncaught browser errors. This second isolated probe was also fully cleaned up.
- A further clean run used `p03-multidivision.mjs seed browser`: 44 teams entered through the database fixture; the 45th manager selected eight riders, chose a captain and submitted breakaway orders in the real browser. The database then contained exactly 45 distinct entries and 45 receipts. Reload retained the orders. The existing admin runner produced three separate 15-team races, and the manager viewed its own replay and division result. The first attempt exposed a test-only assumption that database rider order matched insertion order; the assertion was corrected to check the saved captain ID. The full run then passed and all temporary data was removed.
- The extended `seed browser 3` probe reserved three places and seeded the other 42. Three separately owned managers signed in through separate browser contexts, chose eight riders and a captain, and submitted different breakaway, captain and conserve plans. Their respective order and effort selections survived reload. Each manager then opened their own recorded race and division results after the same 45-team run. The run also checked three 15-team divisions, 60 earned-point awards and an idempotent repeat. The P03 cleanup removed the event, receipts, results, awards and 360 riders; the P02 cleanup removed all 45 temporary accounts and teams. All 275 unit tests and lint passed for this test-harness change.
- A second fresh `seed browser 3` run spread the three reserved managers across the deterministic team-rating order. Each landed in a different one of the three divisions. The browser probe checked the loaded replay's division index and roster, and the loaded result's team list, against the manager's recorded division; neither response contained the other two managers' teams. The own-division selector matched in all three sessions. The full run and both cleanup steps passed again.
- A fresh `seed` followed by `failure` deliberately cleared the isolated fixture event's race tier, then submitted a complete 45-team simulation directly to the atomic race-commit RPC. The point-award trigger rejected the missing metadata at the end of the transaction. All division runs, memberships, team/rider results, ledger awards and race commits stayed at zero; the event remained OPEN, and sampled rider and team state was unchanged. The script restored the tier in `finally`. A subsequent normal `run` succeeded with three divisions, 60 awards and an idempotent repeat; both cleanup steps completed.
- A further fresh 45-team fixture ran `run concurrent`: two simultaneous authenticated administrator requests targeted the same event. Exactly one returned a new commit and the other returned `already_finished`; the existing checks then confirmed three separate 15-team divisions, 360 rider results, three replays, 60 unique award keys and one race commit. A third sequential request also returned `already_finished` without new awards. Both cleanup steps passed.
- The three-manager browser probe now starts at `/team/calendar` rather than a direct event URL. Each manager found the isolated event's calendar card, followed its `Set up` link, selected a lineup and orders, and returned through `My races` to see their own `8/8` team and ready orders before the deadline. All three then watched their separate division replay and result after the 45-team run. The fresh test and both cleanup steps passed.
- The `run concurrent` probe now snapshots all 45 team ratings and all 360 rider ratings before the race. Each post-race balance equals its prior balance plus that team's or rider's saved result points. A sequential repeat compared the full team and rider state, including fatigue, form, injuries and last-raced date, and found no changes. Running the verification command again on the already finished fixture also found no changes. The ledger remained at 60 unique awards and one commit; cleanup passed.
- A fresh three-manager browser run followed the participant path after the entry deadline. One manager opened the viewer from the locked lineup; its `/api/event/prepare` call created the sole race commit before playback. The existing run verifier then checked all 45 teams, three division replays/results, 60 awards and an unchanged repeat, while the other two managers saw their own divisions. This exercises the player-triggered race path alongside the earlier administrator-triggered path.
- The result screen now calls the existing `event_team_results.points` and `event_rider_results.points` values rating gains. Those values increment legacy team and rider ratings; they are distinct from the new earned sporting awards. A fresh three-manager browser run matched each manager's displayed team and rider gain to both the API response and saved result rows. The production build, 275 unit tests and targeted lint passed.
- The division-list endpoint now uses the authenticated route's database client and UUID validation, and returns a fixed unavailable message instead of raw database errors. In another isolated 45-team browser run, each of three managers received their own division and the same 15/15/15 counts; malformed event IDs returned 400 and a request for another manager's `team_id` returned 403. The run, build, 275 unit tests and targeted lint passed.
- A larger fresh probe reserved nine manager accounts: three in each of the three divisions. All nine signed in separately, entered through the calendar, saved a lineup, captain and orders, confirmed readiness, then checked their own replay, division result and stored rating gains after a participant opened the viewer to commit the race. The other 36 entries came from the fixture. The full browser and race checks passed; this expands the real UI coverage without claiming a 45-browser load test.
- The browser probe now follows the race into the separate sporting leaderboard. After the 45-team run it filters to all-time men's Pelotonia one-day team points, then compares an awarded team's stored signed ledger total with the ranking API row and the visible point total. A fresh three-manager browser run passed this database-to-API-to-UI check alongside the existing rating-gain checks.
- A fresh three-manager run used `participant-concurrent` after the deadline: three separately authenticated participants requested preparation together. Exactly one response committed the race and two reported `already_finished`; the database retained one commit, three division replays, 360 rider results and 60 unique sporting awards. All three managers then viewed their own division and the leaderboard matched the ledger. This covers simultaneous player requests in addition to the earlier concurrent administrator probe.
- The additive migration `20261004221018_award_one_day_sporting_points.sql` was applied **only to the isolated test project**. An insert into the existing atomic race-commit table now writes earned one-day rider awards in that same transaction for scheduled events with valid source and tier metadata. The credited team is the rider's result team; tier/placing points are rounded before the recorded division multiplier. Legacy ability ratings continue separately. Unscheduled historic races receive no new awards or backfill. The trigger and points helper have no public client execution grant.
- Two fresh 45-team test races produced 60 positive ledger awards each, covering the top 20 riders of each division. Every award matched its recorded result, tier, year, source, gender and policy version. A repeated admin run left the award count at 60. The filtered team-ranking RPC matched the sum of each team's rider awards. Both test races and every award were removed afterward; the ledger returned to zero rows. Security/performance advisors found no new warning attributable to this migration; existing isolated-project [RLS-no-policy informational notices](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy) and [unindexed-FK informational notices](https://supabase.com/docs/guides/database/database-linter?lint=0001_unindexed_foreign_keys) remain.
- After adding the SQL-error translation, all 275 unit tests and repository ESLint pass. The production build passed before that small message-map change. Vercel also built the exact final commit `2ab82d8` into a READY **Preview** deployment (`dpl_DrgQddyywWc6PeTuGvFTxTbxaNpC`); its target is Preview, not Production. A repeat local Windows build remained at the Next.js start line while consuming CPU, so that environment-specific hang still needs diagnosis. Neither build result verifies production readiness or applies the migration to production.

The `seed`, optional `failure`, `run` or `run concurrent`, `cleanup` sequence in `tests/support/p03-multidivision.mjs` requires `PELOTONIA_P03_TEST_CONFIG` to point to an ignored, isolated-project config. `failure` requires all 45 entries and intentionally moves the fixture deadline to the past, so use it before `run`, not before browser entry. `run` requires `PELOTONIA_P03_AUTH_FIXTURE` for the existing isolated administrator and a local production server at `localhost:3100` with `RECOVERY_ALLOW_GAME_WRITES=true`. `run concurrent` starts two administrator requests together and still performs the normal saved-output and sequential-rerun checks. Always run the P03 cleanup before the P02 team cleanup. The scripts reject a non-allowlisted Supabase URL and refuse to clean a differently named event. They never read production credentials.

For the browser registration probe, run `p03-multidivision.mjs seed browser 9` after seeding 45 accounts, then `tests/support/p03-browser.mjs participant` with both P03 environment paths and the local server, and finally the P03 and P02 cleanup scripts. Use `participant-concurrent` with at least three browser managers to race three authenticated preparation requests; omit the mode to use the administrator runner. The optional count defaults to one and may be 1-45; 45 browser sessions have not been tested. More than one reserved manager is spread across the deterministic rating order; nine managers cover all three divisions with three each. The browser probe submits the reserved entries and finishes the event. It resets only those disposable accounts' passwords in the allowlisted project, keeps passwords in process memory, and never prints them. Plain `seed` still submits all 45 entries through the fixture for an API-only probe.
