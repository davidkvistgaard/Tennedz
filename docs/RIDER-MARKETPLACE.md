# Rider marketplace implementation status

The first version supports fixed-price listings in coins. A signed-in manager can search active listings by name, category, three-letter nationality, age, price and one selected skill; sort by price or the selected skill; list an owned rider; cancel their own listing; and buy another team's rider. The market page deliberately uses initials rather than showing a seller in the buyer's current club kit.

The additive migration `20261029153000_rider_marketplace.sql` stores listings and completed sale receipts, requires one current owner per rider, and restricts the table and four RPC functions to the server's service role. The server checks the signed-in user's team and same-origin POST; `MARKETPLACE_ALLOW_WRITES=true` independently guards market writes while the race recovery switch remains closed. The buy function takes the same advisory transaction lock as the race cycle, rechecks listing state and ownership, refuses riders in unfinished entries or saved lineups, charges the buyer, credits the seller and moves the existing rider link in one transaction. The rider ID, saved appearance and historical race rows remain the same. A sold listing cannot be bought twice.

Local verification on 29 October 2026: two input-validation tests passed; a pinned PGlite PostgreSQL test executed the migration and checked listing, search, purchase, cancellation, unique ownership, insufficient funds, self-purchase, race/lineup refusal and table access controls. ESLint and an isolated 48-page Next.js build passed. One authenticated browser fixture test passed for search, sale, cancellation, purchase and 390-pixel width; it does not use Supabase. Screenshots were inspected.

**Production status, 29 October 2026:** The user explicitly approved the marketplace release. Migration `20261029155824 rider_marketplace` was applied to production project `thacsxtnycmnnpjobgiv`, marketplace writes were enabled independently, and release SHA `05485293a920a071908c08b1b03d1621ecd87e80` was deployed to tennedz.eu. The wider game-write switch stayed closed. A separate Supabase test project verified a concurrent purchase attempt with exactly one success. Production had one team and no listings during verification, so a real two-team production transfer remains unverified.

The rider cards and single-rider profile now link directly to the sale form with that owned rider selected. The manager still has to set a price and submit the listing. A future rider overview can include selected race results and ranking positions once those underlying results and rankings are available as reliable source data; it should link each displayed achievement to its actual race or classification rather than inventing awards or positions.

The 96-hour deadline is measured by the database clock as 345,600 elapsed seconds from the listing insert, independently of the game date and daylight-saving changes. Migration `20261030113000_rider_market_96_hour_deadline.sql` stores the exact `expires_at`, hides expired listings from search, rejects purchases at or after that instant, and archives an expired listing when that rider is listed again. The UI shows the absolute local deadline and a live time remaining counter; the server remains authoritative if a browser clock is wrong. Existing rows retain their original creation time and receive a matching deadline. A status may remain `active` in storage after its deadline until re-listing, while all market reads and purchases treat it as expired.

The site-wide live clock shows the visitor's local date, time, seconds and time-zone abbreviation. `/api/time` returns the current server instant without caching; the client synchronizes at load, every minute and when the tab becomes visible, then updates the display every second. The separately labelled game date is a season state, not the real-time clock used for race and marketplace deadlines. If the time endpoint is temporarily unavailable, the display labels its fallback as device time.
