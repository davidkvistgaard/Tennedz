# Opt-in two-phase race creation in the isolated preview

An administrator can now select a separate tactics deadline when creating a scheduled one-day race, provided automatic entry processing is enabled. Registration closes at the existing entry deadline; the tactics deadline must follow the next 02:00 UTC daily scan by at least 70 minutes and precede the scheduled race. The existing one-deadline creator remains the default. Both gender events use the same opted-in dates, and a repeated request returns the same event IDs. The administrator's race-run button stays disabled until the scheduled start for these events.

Migration `20261005093442_opt_in_two_phase_calendar_creation.sql` adds only a service-role creator that wraps the safe scheduled creator. It was applied **only** to isolated Supabase project `nxhvaoonnvmvohqaxfdx`. The rollback-only `tests/support/two-phase-calendar-creation-probe.sql` checked both saved gender events, idempotent retry, changed-request rejection, invalid-window rejection and fixture rollback. The security and performance advisors reported no new findings caused by this function. The existing private-table RLS/no-policy and older index notices remain. Unit tests, lint, production build and a focused local browser form test passed.

No production database or deployment changed. This closes an event-creation gap, but the two-phase milestone still needs a full real manager-to-simulator-to-replay test. The daily scan schedule and participant fallback should be exercised with persistent isolated events before calling the flow playable.

The local cron regression now demonstrates a 1,000-team scan that exceeds one 35-second request budget: the division stays hidden while the queue is incomplete, and a second authenticated call completes the scan and commits the reveal once. This is a safe failure mode, not a scheduling guarantee. [Vercel's current Hobby limits](https://vercel.com/docs/cron-jobs/usage-and-pricing) allow a cron expression only once a day and permit execution anywhere in the scheduled hour. With only the daily `02:00 UTC` invocation, an interrupted or oversized scan can remain pending beyond registration close, when the queue will no longer claim that event. The next operational increment must provide a durable, sufficiently frequent retry and an alert for an overdue reveal before enabling two-phase calendar races; simply widening the tactics window does not recover missed entrants. Keep the feature disabled in production until that path is tested with persistent isolated events.
